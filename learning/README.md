# Learning

One installed learning engine supports natural study conversations in Claude Desktop, Claude Code and Codex through one local MCP server. The learner asks to explain, continue, practise, review or plan; the tutor teaches and keeps memory quietly. There are no management commands for the learner, no compulsory intake, no dashboard.

## Workspace

A course or project directory owns a hidden `.study/` after `study init`; `.study/course.json` is the course record (schema 7). One workspace studies one course. Notes the learner asks to keep are written to `study-notes/` beside it, where Obsidian sees them. Material stays where it is; relative source paths resolve from the directory. Running from a descendant finds the nearest workspace.

Material that must stay free of study files, such as a code repository, is linked instead: `study init --workspace ~/study/course --sources ~/code/repo` records the material directory in the workspace manifest and in the per-user registry `~/Library/Application Support/Learning/workspaces.json`, which lists every workspace. Relative source paths then resolve from the material, and running from the material or any descendant finds the workspace when no nearer `.study/` exists. A link is used only while the workspace still names the material. `study link DIR` relinks moved material and `study unlink` restores the workspace's own directory. Preferences that apply to every course live beside the registry in `preferences.json`.

```sh
cd /path/to/course && study init
study init --workspace ~/study/course --sources /path/to/repo   # study files kept outside the material
python -m learning.install --study-root DIR                      # offer the MCP server in Claude Desktop and, below DIR, Claude Code and Codex
```

## Agent interface

`python -m learning.mcp` is a stdlib MCP server over stdio. Its tools (`courses`, `resume`, `show`, `search`, `plan`, `list_sources`, `guide` read-only; `save`, `add_sources`, `write_note`; `forget`, destructive) take an optional `course` (title or workspace directory; omitted inside a course folder or with a single course) and run the CLI below; its prompts (`study`, `review`, `mock_exam`, `plan_week`) load the playbook with a fresh `resume`. The installer offers the server only in study folders: Claude Code finds it through `.mcp.json` in each study root (`--study-root DIR`, repeatable and remembered), and Codex through a `.codex/config.toml` in each study root and course folder that `~/.codex/config.toml` trusts; `init` and `link` configure Codex for new courses. The installer adds a trust table only for a folder that has none, each under its own comment line, and removes one only when the folder is no longer a study root or course and the table still reads exactly as written; a table Codex or the user added or edited is never changed. Running it once migrates the old `# Begin learning study folders` block in place. It also links the `tutor` skill for Claude Code and Codex and builds `tutor-claude.zip` for upload to Claude Desktop.

`python -m learning [--workspace DIR] VERB` is the underlying CLI. Every response is JSON on stdout; every failure is `{"error": {"kind": validation|io, "message"}}` on stderr with exit 1, and the message names the field, the fix and close matches.

| Verb | Purpose |
| --- | --- |

| `show HANDLE...` / `show --all` | whole items: a topic with its standing and history, an observation, a knowledge entry, a task, a source, an arc with its topics, standing and log; or everything |
| `map [--here TOPIC]` | the whole course for drawing it: today, exam countdown (with an exam that has a scope, its `arcs`, what it `leaves_out` and the untaught earlier topics it `needed` started first), current topic, open tasks (each with its own `topics`, in the task's order, never the path's: round 9, 2 m8), and every topic in path order with its `needs`, symmetric `contrasts`, level, review date (the day the daily plan puts it), `overdue` when that is today, `starts` (the day the plan starts an untaught topic) with `starts_after` (the courses whose new topics come first) and `starts_why` (why it comes then in the material), the weak verdict and its signals; in a course with arcs, each topic's `arc`, the `current_arc` and every arc with its state, `current`, `hidden` and `entry`; uncapped and without observation text. `--here` as for `resume`. The app's course page reads it; no MCP tool |
| `search QUERY [--all]` | accent-insensitive lexical discovery with light stemming over topics, arcs, knowledge, tasks, sources and observations, in this course or every registered course |
| `plan [--all] [--days N]` | the reviews the daily plan puts today and on the days after, open work, exam countdown, Journal study time, the last 7 days (`week`), the daily plan for the next N days (`plan`: each day's reviews and new topics, and why each new topic comes then (`why`), every course planned together: everything owed until the learner has shown a limit on that weekday, in `capacity`) and, within 21 days of an exam, the run-up (`runup`) |

## Record model

`topics` are the knowledge path: each is one idea or method with prerequisite `needs`, an optional diagnosis (`gap`, `note`) and a `review`. `observations` are learner evidence: one per attempt (with the `help` given, the `result` and, when the learner said, how `sure` they were: `guess`, `neutral` or `confident`), external exam result, or explicit self-report; misrecordings are superseded by a correcting observation, never edited. From them the engine derives one verdict per counted day (`solid`, `helped` or `missed`: the learning day's best grade capped at `helped`, a review day's first try, or a practice day's unaided failure only; a guess is never `solid`) and from the verdicts each topic's level (`new`, `introduced`, `attempted`, `assisted`, `independent`, `retained`, `transferred`), lapses after earlier success, and stale diagnoses. A save that creates or changes a verdict schedules the next retrieval on a successive-relearning ladder (the next day after the learning day, then 1 day after a miss, 2 after help, and 3, 7, 16, 35, 75 and 160 days for consecutive solid verdicts, plus, with no exam ahead, the days a solid review was late); two misses in a row mark a topic `relearn`. With an exam ahead no review lands after the final review, `final_review_days` before the exam (a course preference when the learner sets one; otherwise his pace, the fewest days whose reviews hold one of every topic, read from every course's record whenever the course is read, its start kept on the exam as `final_review` once it has begun), and none on the exam day: a review past it goes to its spaced date after the exam, where the course's reviews go on; setting or moving the exam re-derives every engine date; the tutor can pin a date, a retrieval prompt and its key points. Each `resume` lists today's review: at most five due topics, lapsed ones first, prerequisites before the topics that need them and competing methods (`contrasts`) side by side; a wrongly chosen method is recorded with `chose` and summarized as the topic's choice errors, and a confidently wrong answer as its confident errors. `path` orders the topics and marks the current one; `tasks` hold unfinished activities with their goal, next step and help given; `knowledge` holds what the tutor knows about the course, and its pinned entries, loaded in every session, may not grow past 1536 bytes; course facts and course preferences complete the record.

Saves are merge patches applied to the latest record under a lock and published atomically, refused when their text holds invisible characters; unchanged results publish nothing, and a repeated observation within 30 minutes is skipped, so an uncertain save is safe to retry. Two sessions changing the same field: the later one wins. `resume` returns whole items within byte budgets and lists what it left out.

## Code

`schema.py` defines record shapes, the shared handle namespace, whole-record validation and the patch rule. `arc_rules.py` holds the arc rules that read no evidence (structure, names, the exam's named topics, events, placement range, cleanup), and `arcs.py` those that do (studied, held and current arcs, each arc's `standing` and its `map_block`, the check pairs, the arc notes and the rubric's computable checks in `report`) and the save step that places new topics and guards re-cuts. The current arc is the arc of "You are here": the lesson in progress (`--here`), else `path.current`. `migrate.py` moves records between schemas. `progress.py` derives standings, levels and each topic's open mistakes, and schedules reviews. `records.py` loads the course, publishes saves and receipts, and forgets. `retrieval.py` builds `resume`, `show`, `map`, `standing` and `search` on the one packer in `packing.py`. `planning.py` joins reviews and open work with read-only Journal effort and schedule through `sync.study.context.journal_summary`, and adds each course's week in review, daily plan and exam run-up. `capacity.py` learns from every course's record which weekdays the learner studies and, for reviews and new topics, the limit he has shown by stopping short of what was owed, read against the plan made that morning (a finished plan is only a lower bound, and a day he did exactly what his limit proposed shows nothing, so a night after a finished plan moves no date). A day he was told holds all day: during a day only the topics his study touched (an answer that counts, or a start) take new days, every other keeps the day the plan made as the day began gave it, and a topic's `moved` names what moved a day since yesterday's plan (his study today or yesterday, a day with no study, or yesterday's plan left unfinished). `agenda.py` projects the daily plan for every course together, and its day for each review and new topic is the one date `map`, `resume`, `plan` and a save's receipt report: every review due and each exam's pace of new topics until he has shown a limit, then within it; a topic's first review, and the check of a topic he must relearn, first while no more than its own interval late (what he has just learned, or just shown he does not know, is checked within days, ahead of another course's final review), then a course's final review, nearest exam first, then the reviews an exam's next topics wait on, then every other review by how far past its day it is as a share of its interval, then an exam course's reviews its final review would repeat anyway (so a course with no exam keeps its memory), then courses past their exam, with competing methods reviewed side by side, and nothing of any course on an exam day; new topics only from the ready set, an untaught topic that taught topics need first, paced to finish four days before each final review (whole topics a day, the pace's fraction carried within the calendar week, and never more left to the days after than his limit holds on them), the days a pace leaves going to courses with no exam ahead before any exam's topics beyond its pace, except while a final review runs, when the exams' topics left come first, and a second topic on one day only when a pace or his rate needs it, one that belongs with the first and comes from the same arc. New topics follow the material: the path runs arc by arc, and a topic starts only from the earliest arc with topics left (the arc of the earliest untaught topic, which is not the current arc of "You are here") or the next arc (`NEW_TOPIC_ARCS`), or, in a course whose arcs need nothing from each other (strands with no order between them), any arc; once one arc builds on another, a later arc that happens to need nothing waits its place; without arcs, a topic ahead of the earliest untaught one starts only when it builds on one, so a topic that needs nothing waits its place. An exam's pace passes that window only on a day when holding would raise the pace it needs, or, once he has shown a limit, when his limit on the days left cannot make that day up. Each start carries why it comes then (`agenda.Why`): `next` in its arc, `after` the prerequisites or competing methods it waited on, or `early`, with the earliest arc with topics left (`behind`) and what it waits on; each topic left out before an exam carries why (`agenda.Reason`): no study day left, not ready in time, every day full at his limit, or started too near the exam for a review. An exam with a scope (`exam.arcs` in a course with arcs, less `exam.leaves_out` in any course) examines only those topics: only those take its review dates, final review and run-up, while its pace, gates and what does not fit hold them and their untaught prerequisites (`progress.exam_topics`); the rest of the course is planned as with no exam, before and after it, but for the topics it leaves out, which start only after the exam's day. A course that takes no questions builds on what was taught and schedules no review. `preferences.py` merges global and course preferences and reads the ones the engine uses (`final_review_days`, and `questions`, whether a course takes questions at all). `sources.py` scans and registers material. `notes.py` writes requested notes to `study-notes/`. `storage.py` publishes atomically under locks; `clock.py` owns the study day (`LEARNING_TODAY` pins it for simulations). `cli.py` is the command table and `__main__.py` the entry point; `mcp.py` is the MCP server; `install.py` and `readiness.py` set up and check the hosts; `workspace.py` owns discovery, links and the registry.

Run `python tools/check.py learning` for the focused gate (Ruff, strict mypy, import contracts, Python tests). Tests use synthetic state only. The behavioral acceptance protocol and the dated design reports are under [docs/learning](../docs/learning/README.md).
